# 开发流程 v3 规则

这份文档是我们以后所有项目的开发流程规则。来源有三处：DEV_FLOW v2 的实践、LoomCV 上的 SDD 试行、AI-native SDLC playbook 课程。裁定的原文在 `docs/decisions.md` 指向的笔记里，这里只写结论。

**读法。** 每章分两部分：

- **v3 试行的做法**：从试点项目开始真正执行的做法。
- **只写不启用**：设计写在这里，现在不执行。每条都写了什么情况下再拿出来。

阶段用 playbook 的名字（Plan、Design、Build、Test、Deploy、Maintain），12 个 play 用课程原标题，文件用 SDD 的名字。没有内部的关卡编号。

---

## 总则

### 流程管什么

开发流程只管仓库里产品的改动：代码、站点内容、配置。用这些产品干业务的工作流程（比如用 skill 写公众号文章）不归它管。两边唯一的交接点是：有人在干业务时发现产品需要改，说出来，记成一条待办。

### 三个档位

| 档位 | 什么算这一档 | 走什么 |
|---|---|---|
| 小改动 | 用户察觉不到行为变化，或者只动一处：错字、文案、一个配置值、依赖升级、评审里发现的单处修复 | 一个文件夹，两份短文件（intent.md、validation.md），没有 spec、plan 和问答 |
| 正常档 | 其余全部 | 一个 session 走完：intent → spec 加 validation → plan → 红测试 → 实现 → 评审循环 → 结尾那一屏 → 收尾 → 合并 |
| 高风险档 | 出错的代价高。碰到以下任何一项通常就是：不可逆的数据改动、凭据或个人数据、公开发布或部署配置、已有真实数据的存储或输出形状 | 和正常档同一个形状，再加：plan 写明回退路径；validation 的 §3 必填，并且在真实数据上走一遍 |

- 档位按出错的代价定，不按触发词；界线是定性的，不设文件数阈值。小改动的事后核对靠评审里的固定检查「这次小改动有没有在不止一处改了用户会注意到的行为」：没改行为的，动几个文件都算小改动；只在一处改了行为的单处修复也算。
- **档位是 session 提的，owner 认可。** session 在 intent 里定一个档位并说理由，写 spec 时那一屏「做成什么样」上列出档位和一句理由，owner 说一个词就能改。高风险是 session 的判断，不是 owner 的决定；只有真实数据已经在用的形状才算「数据形状」（飞猫的脚手架因为动了还没有真实数据的形状被判成高风险，是误判）。
- 档位写在 intent.md 的 `Tier` 一行，接受后不再改。
- 档位不决定模型。session 判断出错的代价高时，在那一屏上带着让它这样判断的事实建议一次 Fable，由 owner 定（见「模型」）。
- 小改动也有自己的文件夹，这样「为什么改、怎么改、怎么测的、留下什么没做」都查得到，不靠 Git 历史去猜。
- 不是产品的文件（笔记、roadmap 的状态行、CLAUDE.md 里两次即记的更正、本改动的裁定带来的 roadmap 计划阶段和 `specs/decisions.md` 的修改）直接在工作分支上提交，提交说明里写原因，随改动一起合并。roadmap 的「To do」段例外：它的行不在分支上改（见 Maintain）。凡是碰产品代码、内容、配置的，哪怕一个字，都走小改动。

### 批准记录：`main` 上的文件，和 plan 的批准标记

- intent、spec、validation 被批准，记录就是它们在 `main` 上的已提交版本。在分支上是草稿，在 `main` 上是已接受。intent 和 spec 都没有 `Status` 字段。
- plan 被批准，记录是改动文件夹里的批准标记 `plan-approved.txt`，提交在工作分支上，`main` 不动。标记只由批准写出：Edit 和 Write 写它会被拒绝。
- agent 只在工作分支上工作和提交。钩子拦掉一切会移动 `main` 的 git 命令和 `gh pr merge`，并说明该走哪条路。
- 正常档和高风险档批准三次，按批准的对象命名：

| 批准 | owner 做什么 | 记录 |
|---|---|---|
| 做成什么样（intent、spec、validation 一起） | 答问、逐个确认事实值、UI 改动看 mock 本身并确认、划掉没有意义的判断题、看一屏「做成什么样」，说「接受 spec」 | 三份文件一起进 `main` |
| plan | 在 plan mode 里读「For the owner」一节、追问到满意，接受计划 | 钩子把被接受的计划原文写成 plan.md，记批准标记 |
| 合并 | 看结尾那一屏、答判断题，说「确认合并」 | 分支并入 `main` |

- 「接受 intent」在正常档和高风险档退役，只留给小改动。
- **批准之后默认接着做**，owner 随时可以打断；没有停顿标记。「接受 spec」之后同一个 session 进 plan mode，plan 批准之后接着实现。
- **只有一处可以选停：plan 批准之后。** 交计划之前 session 弹一次问询：批准之后接着实现（默认），还是先停。选了先停，钩子照常记批准，session 只回一行「plan 已提交 <哈希>」就停；owner `/clear` 之后说「继续」，从实现的第一步接上。原因：plan 批准那一刻实现要的东西都在盘上，而上下文里还背着前面的问答（飞猫 `2026-11-21-article-template`：批准时 24%，清掉之后接得顺）。停不由脚本卡住。
- **plan 的批准怎么落地。** owner 在 Claude Code 退出 plan mode 时接受计划，那一下就是批准：`ExitPlanMode` 的 PostToolUse 钩子把被接受的计划全文原样写成 `specs/<文件夹>/plan.md`，写批准标记，两个一起提交在工作分支上。写入钩子认这个标记才放行产品文件。接受之后标记没记上时（钩子没收到计划原文，或插件钩子没在跑），agent 把计划原样写成 plan.md 并提交，owner 说「批准 plan」，写的是同一个标记。批准之后再进 plan mode（比如规划一轮修复）不改 plan.md。
- Test 阶段没有人工批准，靠钩子和 verify 命令。
- **owner 怎么批准：在对话里说一句固定的话。** 立项是「接受立项」，其余见上表；小改动的 intent 是「接受 intent」。整条消息只有这句话才算；空格和标点不计，词序可以反过来（「spec 接受」）；多一个字就是普通消息。消息提交时钩子先于模型运行，直接跑对应的脚本（`accept.py` 或 `merge.py`），把结果交给 agent，agent 接着往下做。「owner 同意了没有」不由模型判断；agent 自己调这两个脚本、或者用 `gh pr merge` 合并，照旧被拒绝。所有档位都能用。
- 小改动另有两次点击（intent 和合并各一次），因为提示里会显示 intent 和改动的文件。点击弹不出来时，说那句话。
- 退路：在自己的终端里粘贴状态报告给出的那一行，跑的是同一个脚本。插件钩子没在跑的 session 里只有这条路。
- 这句话不显示被批准的内容，前提是 owner 读过文件。批准的是说话时所在分支的那个改动，结果里写明分支。
- 界限：这个钩子在三种不是 owner 打字的情况下也会触发（定时唤醒、后台 subagent 的回报、别的 session 发来的消息），而钩子的输入不标明来源。对策有三条：整句匹配；在 subagent 里触发时不动作；agent 排一条内容是批准句的定时任务或跨 session 消息会被拒绝。和别的拦截一样，挡得住 agent 越过批准，挡不住存心绕过。
- owner 打回计划时钩子不触发，plan 不会被记成批准（2026-11-20 实测）。界限：带着一段话批准（在对话框第三项的输入框打字、再按 shift+tab）时钩子触不触发、这段话交不交得到 session，没有实测过，流程不靠它。
- 钩子只查批准记录在不在，不锁内容。批准之后再改，会在最后的 diff 里看到，plan 里的「Spec changed after acceptance」「Departures」两节写明，并计入度量。
- 只有合并之后才有意义的验收，在集成分支上跑；把集成分支合进 `main` 就是批准。

### owner，没有角色表

规则和模板里只用一个词：owner。个人项目上五个角色都是同一个人，角色表在实际操作里不起作用。真正起作用的只有两处：spec 里每条 concern 的 owner（比如飞猫的品牌和内容归 Kitty），以及 intent 用谁的话写、由谁确认。

**owner 坐下来两次。** 开头：说要做什么、答问、逐个确认事实值、UI 改动在浏览器里看 mock 并确认、划掉没有意义的判断题、认可「做成什么样」，接着在同一个 session 里终审 plan（读三个追问的答案和要他裁定的点，追问到满意，接受）。结尾：看一屏结果（做成了什么、清点的结果、判断题、和开头说的不一样的地方、改过的测试、遗留项的去向），答判断题，说「确认合并」。中间的评审、修复、复核、清点由 session 里的 subagent 和脚本做，报告落盘，owner 不读。

中途只在三种情况下找他：开头定的做不到或互相矛盾；同一个问题修了两轮还不过；要做开头没授权的不可逆的事。owner 不写测试，不读代码，不读 §1 和 §2。UI 改动的开头（看 mock）和结尾都需要他坐在屏幕前。

**owner 想要另一双眼睛时。** 他想让人评价 session 自己写的东西（一份文档、一个方案、一段说明），就在同一个 session 里说；session 起一个没有上下文的 subagent，只给它那份东西和一个具体的问题，把它的话报回来。不另开对话，也不为此新增 subagent 的定义。普通的问答、解释、裁定不经过 subagent，照旧是他和实现的 session 直接谈。

### 评审由新上下文的 subagent 做

- 正常档和高风险档：评审是 subagent `reviewer` 的事。它有新的上下文，任务说明只有改动文件夹的名字，自己读 REVIEW.md、改动文件夹和 diff；固定用 Opus（见「模型」）。「评审的不是实现的」这条独立性从此靠新上下文和只给文件夹名来保证，不再靠 owner 在 session 之间传话。
- **「只有文件夹名」写成一句固定的话**（verifier：`Check the change in specs/<文件夹>/. Start with the first step of your checklist.`；reviewer 同形），里面除了文件夹名（预读再加 plan 草稿的路径）没有对改动的任何描述。verifier 和 reviewer 的定义写明第一步必须是工具调用、不自己补写任务说明。原因：只有一个词的任务说明让 verifier 连着两次先替调用方编了一段说明（「第 3、5 项可以跳过」），没跑任何命令就被结束（飞猫 `2026-11-21-sync-flow-templates`）。没查就交回的不算结果，不记、不落盘，重新起；连着三次就找 owner。
- 新开 session 的评审（`review` skill）是 owner 想要时才用的选项，不是固定步骤。
- 小改动：verifier 带着 REVIEW.md 的固定检查给出评审结论。兜底有三条：
  1. verifier 不靠任务说明干活：它自己读 `main` 上的 intent 和分支对 `main` 的 diff，任务说明只有文件夹名。
  2. 合并提示里列出改动的文件和行数，由 owner 自己看，不设行数阈值。文件和行数排在提示的最前面，intent 只留标题一行，整段约十行：提示大约在第十行之后折叠（2026-11-20 两次实测），而 intent 全文在第一次点击时已经看过。
  3. 小改动碰到项目声明的高风险路径，合并脚本直接拒绝。
- 状态脚本报告还有几个小改动没被新 session 读过；owner 要新 session 评审时，它把这些逐个读一遍，判断行为变了没有，记进各自的 Approval log。被判为「本该走正常档」的个数是试点后决定要不要收紧的依据。

兜不住的部分：改了行为的小改动合并之后就在线上，不再有固定的事后复读。坏发布代价可接受的项目接受这一点（回退那次合并）。

### 每个改动一个文件夹，状态从 Git 读

- 文件夹是 `specs/<日期>-<slug>/`，工作分支和文件夹同名。`specs/` 顶层放 mission.md、decisions.md、roadmap.md。按日期排列的文件夹就是全部改动的索引，大小改动都在。
- 现在在哪一步，由状态脚本从仓库推出来：当前分支对应哪个文件夹，intent、spec、validation 在不在 `main` 上，plan 的批准标记在不在，红测试提交了没有，Approval log 里最新的评审行和验收行。钩子和收尾检查读的是同一批事实。会话开始时钩子自动跑一次状态脚本。
- **一个改动一个 session。** 上下文过长主要靠拆小（见 Design），落盘是兜底：报告、裁定、验收的答案都在改动文件夹里，session 断了或被压缩之后，新开一个说「继续」就能从状态脚本报的那一小步接上。
- **合并之后工作分支就删掉。** 合并脚本在 `main` 前移之后把检出切到 `main`，删除工作分支，远端有同名分支也一起删；立项验收之后 `setup` 分支同样处理。`main` 被别的 worktree 占着、切不过去时不删，脚本打印要手工做的两行。停在一个已经合并的分支上时，状态脚本报「Merged」，这时说「确认合并」只做清理。
- **有远端的项目，本地 `main` 和 `origin/main` 保持一致。** 每个移动 `main` 的脚本先把 origin 上的新提交快进进来，做完再推上去。只做快进：两边分叉时拒绝，并给出 owner 手工处理的那一行。在 GitHub 上合并了流程之外的 PR（比如例行内容）之后，用 `sync_main.py` 把本地 `main` 快进到 `origin/main`；agent 可以直接跑，因为批准已经在 GitHub 上发生，agent 推不了 `main`，也合不了 PR。开新分支之前也先跑它。

### skill 和启动方式

- 每个步骤是一个 skill，用平常话触发，没有带参数格式的命令。保底的启动方式是 `/flow:<名字>`；名字后面跟的内容当作普通指令读。
- 每个 skill 结束时用一句话说下一步是什么。
- 清单、每个 skill 测试通过的说法：见 `docs/skills.md`。

### 钩子分三类

- **直接放行或拒绝，不需要人**：移动 `main` 的 git 命令、`gh pr merge`、存在检查、在分支上改 roadmap 的「To do」段。
- **问操作者（`ask`）**：只用在操作者有权批准的地方。个人项目上 owner 就是操作者：小改动的两次点击、roadmap 待办行的删除和移动。
- **检查一份已记录的批准**：批准人是别人时用。个人项目上就是「文件在不在 `main` 上」和「plan 的批准标记在不在」。agent 没有办法自己写出它要被检查的那份记录。

拒绝时总是说明该走哪条路。界限：按模式匹配的拦截挡得住 agent 越过批准，挡不住人绕过去。

另有两个不属于这三类的钩子：消息提交时认出 owner 的批准句，直接运行对应的脚本；owner 在 plan mode 里接受计划之后，写 plan.md 和批准标记。见上面「批准记录」。

核心不带「禁止用 shell 写文件」的钩子：plan mode 本身不让写文件，合并前按差异查的两项（测试范围、plan 对照）对 shell 写的文件同样管用。

### 模型

模型由 owner 选。用户级的模型表（`plugin/templates/user/model-table.md`）只是参考，不在流程核心里。要点：

- **干活**：主 session 默认 Opus，小改动 Sonnet。效果不理想（测试不过、卡住、同一个问题修了两轮还不行）时停下来说明，owner 先加 effort，再决定换不换；要换就在这个 session 里换（`/model`），不另开 session。session 不自己换。
- **核查**：verifier 和 reviewer 两个 subagent 固定用 Opus，写在它们的定义里，不管主 session 用什么（小改动由 Sonnet 做，核查照样是 Opus）。原因：干活的效果不好看得见，核查的效果不好看不见——漏掉问题的评审和干净通过的评审报出来都是 0 条 Important（飞猫第一个改动的 verifier 第一次跑报 0 条，同样的代码第二次跑才查出不存在的日期会崩溃），所以核查不等「发现不理想」再升。code-reviewer 只看规范和可读性、researcher 只查事实，不算核查，跟主 session。
- **流程只在两种时候建议 Fable**：判断出错的代价高（写 spec 时那一屏上，带着事实建议一次：核查用 Fable，或整个改动用 Fable）；加了 effort 结果仍然不理想。换不换由 owner 定。owner 接受了核查用 Fable，实现的 session 在调用 verifier 和 reviewer 时指定 `model: fable`：调用时指定的模型盖得过定义里的 `model`（code.claude.com 的 sub-agents 页）。

## 立项

在六个阶段之前，每个项目做一次。

### v3 试行的做法

- 写三份项目级文件，放在 `specs/` 顶层。立项在名叫 `setup` 的分支上做，立项时写的所有文件都提交在这条分支上：
  - **mission.md**：用户是谁、带着什么来、带着什么走、中间做什么、这个产品不做什么。只有这五个标题，一屏左右。用处有三个：问答时先查它，查得到的范围问题不再问；每份 intent 的「Out of scope」对着它写；Maintain 阶段据此驳回一条待办。
  - **decisions.md**：CLAUDE.md 没有锁定的项目级决定：产品的形态和技术栈、工作怎么组织、怎么发布；用一句话回答「生产环境宕机或出错几天，代价是什么」；要部署的项目有「Deployment」一段（见 Deploy 一章）。还没定的事不写在这里，记成 roadmap「To do」的一行。写 spec 时它是约束的来源；以后新的项目级决定也加在这里。
  - **roadmap.md**：顶部的状态行（下次从哪里接着做）、按顺序的计划阶段、「To do」段、「Known limits」段。
- 同一步里写好项目的 CLAUDE.md、REVIEW.md、`.claude/flow.json`。仓库里有 `.claude/flow.json`，钩子才动作。
- **这三份是从插件模板抄来的，带一行版本标记**（`flow-template: <日期> <短哈希>`，哈希是模板内容的）。项目副本的标记和插件模板的不一样、或者副本没有标记时，状态脚本报一行「这几份和模板不一致」；同不同步由 owner 定，同步之后把模板的标记原样抄到副本上。标记不手写：模板的由 `tools/template_marks.py` 写，自测查它和内容对得上。带哈希的原因：只有日期时，同一天改两次模板，分不出项目拿的是哪一版（飞猫 `2026-11-21-sync-flow-templates`）。mission、decisions、roadmap 是项目自己的内容，不带标记。
- **立项也跑问答**，规则是 Plan 一章「问答是有界的多轮」那一条：先把三份文件和 `.claude/flow.json` 的五项都起草出来，一轮的问题一起给，每裁定一条把剩下的连同默认答案再列一遍。和单个改动有三处不同：mission 和 decisions 正是要写的东西，「先查」查的是仓库里已有的文档；完整性清单是给单个改动写的，这里不用，只在「这一轮没让草稿发生任何变化」时停；停下时还没定的，记成 roadmap「To do」段的一行，不再问。
- **立项验收带整条 `setup` 分支。** owner 说「接受立项」，`main` 前移到 `setup` 的头，和合并是同一个机制，所以立项时写的其他文件（盘点、CLAUDE.md 指向的说明）一起进 `main`。交接前先把清单给 owner 看：项目级文件在前，其余列在「also carried」下，没提交的文件单独列出。不设拒绝，由 owner 自己看。验收后检出切到 `main`，`setup` 删掉。
- 以后改这三份文件：在工作分支上改，owner 说同一句话。这时只提交项目级文件，提交说明里写原因。
- 一份 intent 和 mission 冲突时，先改 mission，再往下做。没有哪份 intent 可以悄悄越出范围。
- 三份文件不全在 `main` 上时，状态脚本报「项目未立项」。
- `.claude/flow.json` 只存脚本和钩子要读的五项：`test_scope`、`deploys`、`pull_request`、`high_risk_paths`、`non_product_paths`。`deploys` 表示「现在合并会不会发布」：只在合并本身触发发布时为 true，流水线接上的那个改动里才改成 true。verify 命令在 CLAUDE.md，坏发布的代价和部署方式在 decisions.md，权限清单在 `.claude/settings.json`。任何 policy 都不进这个文件。

### 只写不启用

没有。

## Plan

### v3 试行的做法

**Capture as intent.md**

- 一份 intent 只讲一个改动：问题（带一个数）、想要的结果、受影响的人和系统、约束、未决问题、不做什么、来源。写「要什么、为什么、为谁」，不写「怎么做」。
- 「来源」一行写谁提的、什么时候，或者是哪个改动的遗留项，这样能倒着查回去。
- intent 和 spec、validation、plan 放在同一个文件夹里。
- **问答是有界的多轮。** 每一轮都挂在一份草稿上：先按已知的写草稿，问题从草稿的缺口来，答案更新草稿。一个问题要同时满足三条才问：仓库、mission 和 policy 里查不到答案；带默认答案；说明答错了要返工多少。一轮的问题一起给；每裁定一条，把剩下的连同默认答案再列一遍。
- **什么时候停。** 完整性清单满足了，或者这一轮没让草稿发生任何变化。清单是：问题带一个数；每条约束在 spec 里有位置；空、错误、首次使用、再次使用四种状态写了；不做什么写明了；没有无主的 concern。停下时还没解决的，记成 concern，不再问。
- **问答用在哪。** 立项、intent、spec 三处。plan.md 和评审不跑问答。plan：需求在 spec 里已经问完，剩下的是实现上的选择，列在「给 owner 的一节」里各带默认、一次裁完；这里还要多轮问，说明 spec 那轮问粗了，由「问得太粗」那项度量去抓。评审：价值在新上下文独立读、独立下结论，边评边问 owner 就又依赖实现时的语境。
- intent 写完不停，直接进问答，接着写 spec；intent 和 spec、validation 一起被接受。
- owner 不是开发者时（飞猫），给她的问题少、用她的话、一批问完，由开发者转达。
- 问答抓不到两类东西：只有在屏幕上才看得出的（靠 mock），只有读代码才发现的（靠在某个 HEAD 上核过的事实和 plan 批准）。
- **小改动**：owner 或者发现问题的 session 说「按小改动处理」，agent 起草四五行的 intent，弹出确认，owner 点一次；之后自动往下做，停在合并前。

### 只写不启用

- **agent 自己写完整的 intent 放进队列。** 这是给无人值守的维护循环用的形式，见 Maintain。

## Design

### v3 试行的做法

**Requirements and design**

- **spec.md**：需求是原子的、可测的，一条一个 R-ID，包括空、错误、首次使用、再次使用四种状态；设计；intent 里每条约束和每个未决问题的去向；**事实值表**（产品要显示或存储、来自代码之外的值，如名称、价格、地址、审定的文字：值、出处、谁确认、确认的是内容还是版式；owner 在开头逐个确认，没人确认的值不做进去）；researcher 在某个 HEAD 上核过的代码事实；对以前决定的修改；带编号的 concern（类别、提议、owner、裁定），裁定直接写进那一行；UI 改动另有「Mock」一节（见下面「mock 评审」）。
- **validation.md** 是独立的文件，在 plan 之前写。正常档六段，按「谁来执行」分：

| 段 | 谁执行 | 内容 |
|---|---|---|
| §0 清点 | session | 能数、能对照的步骤：一次性的准备；每一步是能直接粘贴的命令块，加一句预期结果；真实数据那边不能碰什么。session 在结尾自己跑（终端或浏览器），结果列成表。给另一个会话或另一个人照着做的文档，清点步骤是：起一个只拿到这份文档和一份样例的 subagent 照着做，产出交给机器检查 |
| §0 判断 | owner | 只有他能答的问题，各带编号（J1、J2……）和一句「答对说明什么」。对象是测试材料的、已经裁定过的（确认过的 mock 的版面算已经裁定）、说不出答对说明什么的，不出。**一个没有上下文的 subagent 实际做一遍就能回答的题不是判断题**，写成清点步骤 |
| §1 测试要求 | 实现的 session | 每个「断言还不存在的产品行为」一行，引用 R-ID；核对材料（样例、夹具、记录）不进 §1，归 §2。plan 据此给测试命名和计数；判断「红测试事后有没有被削弱」也看这张表 |
| §2 机器检查 | verifier、评审的 subagent | 这个改动特有的检查：一条命令加预期输出。没有就省略 |
| §3 预期变化 | session 跑，owner 看 | 只在验收会碰真实数据或真实环境时写：什么会变、什么必须逐字节不变、比较用的命令。高风险档必填 |
| Leftovers | 收尾检查 | 每条指向一份新 intent 或 roadmap 的一行 |
| Approval log | 脚本和人 | 放在最后，只追加；脚本要读的行由 `record.py` 写 |

- 没有单独的「失败」清单：§0、§2、§3 的任何一步和预期结果不符，就是失败。
- **一屏「做成什么样」。** 交给 owner 接受之前，session 用一条消息给出：档位和一句理由（owner 说一个词就能改；判断出错代价高时，后面带着事实建议一次 Fable）；做完之后什么成立、不做什么；事实值和各自的确认；UI 改动的 mock 和确认人；结尾要问他的判断题（他划掉没有意义的）；还开着的 concern 和默认答案。他说「接受 spec」，三份文件一起进 `main`。
- **拆小。** 避免一个 session 的上下文过长，主要靠拆小；不设 R 条数的线。出现以下任何一种就拆：结尾的判断题分成互不相干的几组；动了不止一个子系统；有一步单独合并也成立。拆出来的是独立的改动，各有文件夹；暂不做的那几部分是已经定了要做的事，写进 roadmap 的计划阶段（在工作分支上改，随改动合并），不进「To do」。
- 小改动的 validation.md 是五项：改了什么（一行）、verify 命令和粘贴的输出、评审结论、遗留项、Approval log。
- **R-ID 覆盖检查。** 把 validation.md 提交进 `main` 等于批准整份文件，而 owner 只读 §0 和 §3。所以有一个脚本把关：spec.md 的每个 R-ID 至少要出现在 §0、§1、§2 之一，否则拒绝提交。「有没有哪条需求没人检查」由脚本回答。
- 每条命令在写的时候由 researcher 对着「执行那一步时仓库的状态」试跑一遍。
- UI 改动先出 mock，问版面和措辞的问题对着 mock 问。
- **mock 评审。** 对 UI 改动，mock 就是设计，owner 接受设计靠看它本身，不靠读关于它的文字。问答之后、那一屏之前单独做一步：
  1. **定基准。** spec 的「Mock」一节写明 mock 对照的是什么：它取代的旧 mockup 或现有页面；全新的页面写「无」。
  2. **逐块对比，不由写 mock 的 session 自己列。** researcher 拿基准和 mock 对比，列出每一处看得见的差异；它的任务说明只有两个路径，不带意图。
  3. **每处差异要么有出处，要么改 mock。** 对得上一条需求或裁定的，记进「Mock」一节的差异表；对不上的是无意的，改掉。
  4. **有人看过 mock 本身。** session 告诉他怎么打开、按哪几个宽度看，给他差异表，问一次认不认可。他要改的记成裁定，mock 改完再对比改过的那几块。
  5. **记下确认人，脚本把关。** 「Mock」一节写 `Confirmed by: <谁>, <日期>`，只在那个人看过之后写。改动文件夹里有 `mock.html` 而这一行空着，「接受 spec」被拒绝，收尾检查也拒绝。
  6. **之后 mock 就是合同。** verifier 拿做出来的页面截图对它；结尾的判断题不重开版面（已经裁定过的不出题）。owner 结尾仍要改设计，照「接受之后改了 spec」处理，会被计数。
  原因：飞猫 `2026-11-21-article-template` 的 mock 随 spec 一并接受，那一屏只用一行指向它，页脚和旧 mockup 不一样没有人看到，实现之后才被提出来，多了一轮修复。
- 改动碰到产品调用的模型的行为（提示词、模型、检索参数、阈值）时，§2 写上项目的产品 eval 命令和预期结果。这是规则里和产品 eval 唯一的连接点。

### 只写不启用

- **一遍成稿、事后一次性提问。** playbook 的形式是 Claude 一遍写完 spec，把问题列成 concern 清单问一次。那是给无人值守运行设计的；我们用上面的多轮问答。

## Build

### v3 试行的做法

**Plan mode**

- plan 在 Claude Code 的 plan mode 里起草，和 spec 是同一个 session。内容：给 owner 的一节，固定四样（什么可能坏、哪一步风险最大、没选的方案和原因、要他裁定的点，各带默认）；会改的文件，一个路径组一行；工作顺序（测试运行器还不存在时，先一步只建工具链骨架：清单文件、lock 文件、测试运行器，不含产品代码；然后是 §1 的测试，按行命名和计数）；风险；证据（UI 改动包括「截图和 mock 一致」）；「Spec changed after acceptance」和「Departures」两节。每一行引用 R-ID 或 concern。
- 标准：一个没看过这段对话的工程师只凭这份 plan 就能实现。这是停笔的标准，不是换 session 的程序。
- 交给 owner 之前，评审的 subagent 先把 spec 和 plan 预读一遍（任务说明是文件夹名和 plan 草稿的路径），发现的问题改进 plan 或列成裁定点。
- 交计划之前 session 做两件事：弹一次问询，问批准之后接着实现还是先停（见总则「批准记录」）；用两句话告诉 owner 对话框怎么用——「Tell Claude what to change」加回车是打回，两个「Yes」都是批准，在第三项上按 shift+tab 也是批准（框里有字就带着这段话，框是空的就是直接批准），所以想打回时不要按它。
- owner 读「For the owner」，追问到满意，在退出 plan mode 时接受计划：那一下就是批准。之后按他选的：同一个 session 接着实现，或停下等他说「继续」。
- 实现时偏离 plan，在同一次提交里写进 plan.md 的「Departures」并更新文件清单；接受之后改了 spec 或 validation，写进「Spec changed after acceptance」，带它依据的 owner 裁定。脚本在收尾前比对：改了的产品文件必须在 plan 的文件清单里（续行上的路径也算；方括号按字面算，如 `[slug].astro`）。
- 高风险档：plan 写明回退路径（坏发布代价可接受的项目只需写明路径，不演练）。

**The CLAUDE.md**

- 项目的 CLAUDE.md 控制在一页以内：命令和健康输出的样子、「Verifying your work」一段、规范、架构、Claude 在这里容易犯的错、指路。
- 两次即记：同一个错被纠正两次，就在第二次纠正的那个 session 里写进 CLAUDE.md。评审里第二次指出的错也一样。评审还要指出哪一行被这次改动弄过时了。
- 用户级的 `~/.claude/CLAUDE.md` 放我们对 agent 写的代码的规范：名字说清装的是什么（长名字可以）、难懂的地方和「为什么」要有注释、注释和代码一起改。

**Skills as institutional knowledge**

- policy 是规则，config 是项目设定，skill 是把规则包装给 Claude 用的建议性手段。三者不混：policy 不进 config。
- 一条必须成立的规则，背后要有一个脚本，skill 和钩子用同一个脚本。
- 新的 skill 和新的 subagent 都是「收割」出来的：同一件事在主 session 里手工做过两三次之后才做成 skill 或 subagent。

**Parallel sessions and subagents**

- 核心带四个 subagent，都只汇报不动手；它们的报告由主 session 原样写进改动文件夹的 `reports/`：
  - **researcher**：读代码和文档，带文件、行号和 HEAD 报事实；提问之前先查；数据形状要变时列出现有断言；试跑 validation 的命令。
  - **code-reviewer**：按我们的规范查 diff：命名、注释、长函数、深嵌套、重复逻辑。
  - **verifier**：在评审之前最后跑，前台跑，跑在要交出去的那个提交上（之后再改代码就重跑），报告写明查的是哪个提交。跑 verify 命令，查改动的行为和最近的两条流程，按一份必试输入的清单试（空、边界、不存在的日期、超长、类型不对、非 ASCII 和非法编码、重复），逐条对 plan.md；UI 改动对 mock 截图，观察一次调用的全程。开始前看端口有没有被占，结束前停掉自己起的进程、删掉自己建的克隆，报告里列出还留着什么。
  - **reviewer**：新上下文的评审，任务说明只有文件夹名。两件事：plan 交给 owner 之前预读 spec 和 plan；verifier 之后按 REVIEW.md 评审分支，列出修复之后要重看的验收步骤。
- 项目可以在自己的 `.claude/agents/` 下加 subagent（飞猫大概会有一个对照内容规则的检查，能用脚本做的用脚本）。
- 并行：一条流一个 worktree，从两条开始，上限由评审跟不跟得上决定。plan 里写「Parallel split」：共用的一步先做完并冻结，各条流的文件互不重叠，合并顺序和合并后的检查。
- 浏览器在测出结果之前按最保守的读法：一次只给一个 session 用。
- **两个改动交错着走**（未实测，见 `docs/pilot.md` 试点清单第 11 条）。一个改动从开场到合并，慢的是 owner 的两次坐下来，不是机器（飞猫 `2026-11-20-blog`：墙钟 6 小时 23 分，实现和评审循环 69 分钟）。所以有用的交错只有一种：改动 N 在无人值守地实现和评审时，owner 做 N+1 的 intent 和 spec 问答。
  1. 一个改动一个 git worktree、一个分支、一个 session。
  2. 最多两个，阶段错开，不同时等 owner。依据：owner 一次只能坐在一个改动前面；两个都跑无人值守的那段，省的只是机器时间，周用量消耗更快。
  3. N+1 写到 spec 待接受为止。什么时候说「接受 spec」由 owner 按两边改的文件重不重叠定：重叠就等 N 合并之后再接受（接受之后 session 直接进 plan mode，plan 在当前 HEAD 上核代码事实，N 没合并时那是旧代码）；确定不重叠可以直接接受，plan 起草到接受对话框再停。这一条不用脚本：「接受 spec」本来就是他单独的一条消息。
  4. 代价：N+1 的「接受 spec」会让 `main` 前进，N 收尾时要把 `main` 合回来；各自的改动文件夹不冲突，`roadmap.md` 的状态行会撞。

### 只写不启用

- **同一个规则脚本在 CI 里再跑一遍。** 等项目有了 CI 再加。
- **auto mode。** 官方文档写明 auto 模式下钩子的 `ask` 一定会弹提示（2026-11-17 查）；其他权限模式下弹不弹、提示里能显示多少字，试点里测。测完之前不靠它；点击弹不出来时的退路是批准句。
- **两条以上的并行流。**

## Test

### v3 试行的做法

**Give Claude a feedback loop**

- 一条 verify 命令，写在 CLAUDE.md 里，实现时反复跑到绿。「做完了」的证据是粘贴出来的原样输出，不是对输出的描述。
- 每个正常档和高风险档的改动都先写红测试：按 §1 写测试，先对测试文件跑格式化，跑 verify 确认它们因为需求还没实现而失败，把原样输出存成 `red-run.txt`，和测试一起提交在工作分支上。
- **测试锁。** 从红提交起到合并为止（小改动是整条分支），锁住的是那时已经存在、在测试范围内的文件。测试范围在 `.claude/flow.json` 里声明。改测试不询问 owner。
  - 正当的测试修复：agent 改，当场用 `record.py test-release` 在 Approval log 里记一行：哪个文件、为什么、属于 §1 的哪一行，以及文件当时内容的哈希。评审的 subagent 查它有没有削弱 §1 的那一行；结尾那一屏列出改过的测试。
  - 放行只管记下的那个版本：记过放行行之后文件又变了，就要再记一行（评审看过新版本之后）。
  - 新建的测试文件不要求放行行（新测试削弱不了旧测试），结尾那一屏一并列出。新建的配置类测试文件（`conftest.py`、测试运行器的配置、共用的 fixture）能让旧测试被跳过或改变，由 REVIEW.md 的固定检查「New test-setup file」读，不另加设定。
  - 收尾前的检查：脚本比对锁开始时和当前状态之间测试范围的差异，每个有变动的已有文件，最新一条放行行的哈希必须等于文件现在的哈希，否则拒绝。这样不管是谁改的（格式化工具、shell 命令）都查得到。
  - 「红测试是否已提交」由状态脚本从 Git 读 `red-run.txt`，没有标志文件，也不存哈希。
- UI 改动由实现的 session 在浏览器里自查：实现、截图、和 mock 比，两三轮，然后才给人看。

**Continuous evals in CI**

「eval」这个词不单独用，因为它指三样不同的东西：

| 名字 | 测什么 | 放在哪 | v3 怎么跑 |
|---|---|---|---|
| 插件 eval | `flow` 插件的 skill 在平常话下会不会被选中 | 本仓 `plugin/evals/`，官方 `claude plugin eval` 的格式 | 启用。手动，在 owner 的终端里，用订阅登录、不配 API key；`--ablation none`，每个用例跑三次，只用确定性检查。改了某个 skill 的 description 之后跑它的用例；试点开始前整套跑一次。不定期跑 |
| 项目配置 eval | 一个项目的 CLAUDE.md 和项目钩子能不能让 Claude 把活干到标准 | 那个项目的 `evals/`，课程第 9 节的格式 | 只有两种由事件触发的手动用法，见下 |
| 产品 eval | 产品调用的模型表现如何 | 项目自己定 | 项目自己的事。规则只管一个连接点：validation §2 |

- 项目配置 eval 的两种用法：**删除或重写配置之前**（精简 CLAUDE.md、重写一个 skill），给每条要删的内容写一个用例，在交互 session 里手动跑，确认行为没变；**agent 写的代码引发事故之后**，代码补回归测试，配置补一个用例。每个用例跑三次才算数。
- 不定期跑的理由：我们的配置只有 owner 和我们的 session 在改，几乎都是加一行；配置变差会在真实工作里表现为一次通过率下降、修复轮数变多、同样的错重复出现，这些从 Git 和 Approval log 读得到。
- LoomCV 的 `dev_flow/eval/t1/` 全部是产品 eval，原地不动。

### 只写不启用

- **项目配置 eval 的 CI 形式**（每次改 CLAUDE.md、`.claude/`、`evals/` 就跑核心子集）和**定期形式**（整套按周期跑）。
- **多少次运行才可信。** 单次运行不算数。一个用例在某份配置下过不过，按每个用例三次运行判断，和官方插件 eval 的默认值一致；三次结果不一致时，先把用例的检查改得更确定，再重跑。
- **用例从哪来。** 近期真实任务加上每次由 agent 代码引发的事故；一个用例要先在旧配置下失败才算数；素材就是 `specs/` 下的历史（之前的提交、当时的 intent、plan 的文件清单、validation §2）。
- 什么时候拿出来：项目有了真实流量和事故；公司环境里有 API 预算；或者上面那几个度量无缘无故变差。
- 关于费用：用订阅登录时，`claude -p` 用的是订阅自己的额度，不另外花钱。不启用的原因是我们的项目多数是小的个人项目，没有上 CI 和遥测循环的理由，而且每周额度也是实在的成本。

## Deploy

### v3 试行的做法

**AI in the PR review loop**

评审在实现的 session 里循环，到 0 条 Important 才找 owner：

1. **code-reviewer**：只看规范和可读性。
2. **verifier**：最后跑、前台跑、跑在要交出去的提交上（见 Build）。
3. **reviewer**：新上下文的 subagent，任务说明只有文件夹名，按 REVIEW.md 固定的三遍（bug 和逻辑、安全、对 spec.md 和 plan.md 的符合度）和固定检查，每条发现标 Important 或 Nit，列出修复之后要重看的验收步骤。固定用 Opus，owner 选了 Fable 时调用里指定。

有 Important 就修，从第 1 步再走一遍；reviewer 复核上一轮的 Important。0 条 Important 时循环结束，进入结尾那一屏。

- 第 1 层和第 3 层的分工写在 REVIEW.md 的「Do not report」里：风格和可读性归 lint 和 code-reviewer。
- 每条 Important 都要写怎么确认（一条命令，或 validation 的某一步）。「validation §0、§2、§3 的某一步照原文执行和预期不符」一律算 Important，哪怕产品是对的、错的是记录。
- **报告落盘。** 三个 subagent 的报告由主 session 原样写进 `specs/<文件夹>/reports/` 并提交。没改的发现逐条写去向，三种：Leftovers 的一行；「不记」（只限 session 判断代价可以忽略的 Nit，写进 validation.md 的「Not recorded」一节，一条一行）；或一句不做的理由。只写「没改」不算。「不记」的原因：每条遗留项以后都要 owner 处置一次，飞猫 `2026-11-20-blog` 一个改动的 Nit 让「To do」从 8 行涨到 15 行，其中有几乎不会发生的；Git 历史和 `reports/` 里查得到。
- **评审行由实现的 session 调 `record.py review` 写**，脚本写时间和格式，要求报告文件已经在盘上、产品文件没有未提交的改动，并在行里记下被评审的提交（`at <短哈希>`）。收尾检查拒绝「评审之后产品文件又变了」：评审之后再改代码，评审循环就要再走一遍。飞猫第一个改动里 verifier 和评审跑在最后一批改动之前出现过三次。界限（owner 已接受）：写这一行的就是被评审的 session，它可以记一次没有发生的评审；记了之后的改动查得到。
- 新开 session 的评审是 owner 想要时才用的选项（`review` skill），报告同样落盘，用同一个脚本记行。
- **结尾那一屏**（`validate` skill）：清点由 session 做——跑 §0 的清点步骤、§2、§3，结果列成表；owner 只答判断题，每题是通过、不通过、或「这题不判断」。「不记」的那一组发现在这一屏上列成一块，owner 整组认可，或者点名哪几条要留——留的改成 Leftovers 的一行；他的回答用 `record.py ruling` 记一行。「这题不判断」记一行，并在 Leftovers 留一条带去向的遗留项，收尾检查不拦。答案由 `record.py validation` 记成验收行，收尾检查读它。不通过的在同一个 session 里修，评审循环再走一遍，只给 owner 看改动的部分，再问一次。
- owner 中途给的裁定，先对 §0、§3 和 spec 里的事实核一遍再动手，用 `record.py ruling` 记一行。
- 有 PR 的项目另外把 `reports/` 里的报告贴成 PR 评论。
- code-reviewer 留不留，试点之后判断，事先不设阈值：数它的发现里有多少导致了代码改动。

**Hooks as approval gates**

钩子和脚本的完整清单见 `docs/hooks-and-scripts.md`。合并之前，脚本确定性地检查：每份文件的形状、R-ID 覆盖、测试范围的差异、plan 对照、遗留项的指向、分支自己没有动过「To do」段、有 mock 的改动写了确认人、最新的评审行没有未处理的 Important、报告在盘上、它记的提交之后产品文件没有再变，最新的验收行（每道判断题都有答案、没有不通过、不判断的都在 Leftovers 里）。任何一项不过就拒绝，并说明缺什么。

- **检查因为自己的毛病拒绝时**（它读错了一份本来没错的文件），session 停下来报给 owner：哪一项、为什么判断是检查的毛病、打算怎么绕。owner 同意之后才动已批准的文件，并用 `record.py ruling` 记一行。
- **收尾在同一个 session 里接着做。** 待办的遗留项一次提交进 `main`（`todo_add.py` 一次收多行，「谁提的」可以按行给），之后把 `main` 合进工作分支，再改「Known limits」和状态行。状态行写的是合并之后的状态，不出现「等待合并」一类的话。

**CI/CD integration and deployment**

- **部署方式按项目定，立项时写进 decisions.md 的「Deployment」一段。** 流程不规定形式，只要求回答五项：怎么发布、什么触发、部署凭据放在哪和谁（或什么）够得到、怎么回退、发布由什么批准。
- **推荐做法**，没有理由不用时就用：由合并触发发布，凭据放在 agent 够不到的地方（CI 的 secret 存储）。它不增加工作量，保证「不合并就不会上线」，合并同时就是发布批准。这是推荐，不是硬要求：飞猫的主路线是这样，它的备用路线（agent 在 owner 已登录的浏览器里经 cPanel 上传）不是。
- 其余要求按坏发布的代价分级，依据是 decisions.md 里那一句话：
  - **代价可接受**（飞猫）：不设 staging，发布前在本地预览里验收；回退按 Deployment 段写的那一行做，不演练；不要求发布后的自动检查。
  - **代价不可接受**：见「只写不启用」。
- **合并触发发布的项目，合并就是发布批准**（代价可接受的项目）。owner 的「确认合并」同时批准了代码和发布，没有单独的发布步骤。合并前的确认要写明后果：小改动的合并提示里带一行「Merging publishes to production」；走 PR 的改动，这一行放在 PR 描述的固定位置。带不带这一行由 `.claude/flow.json` 的 `deploys` 决定，它表示「现在合并会不会发布」：只在合并本身触发发布时为 true，流水线接上的那个改动里才改成 true。合并脚本的提示也按它说。
- **合并不触发发布的项目**（发布是合并之后单独的一步，或者项目换到了这样的备用路线）：`deploys` 设 false，合并提示和 PR 描述不带那一行，「合并就是发布批准」不适用。Deployment 段写明发布由谁、以什么动作批准，那个动作才是发布批准。
- **个人项目上的批准就是 owner 自己的合并。** GitHub 不允许作者批准自己的 PR；缺少的第二个人的检查，由新上下文的评审 subagent 和 owner 在结尾那一屏的判断补上。
- **开不开 PR 按项目定**，写在项目的 CLAUDE.md 和 `.claude/flow.json` 里：有远端和部署流程的项目开 PR；只在本地的项目不开，评审在分支对 `main` 的 diff 上做。PR 在收尾时才推、才开。
- **走 PR 的项目，「确认合并」由脚本合并 PR**：跑收尾检查，核对 PR 的头就是本地分支的头，`gh pr merge --merge`，再把本地 `main` 快进到 `origin/main`，切过去，删分支。owner 在 GitHub 页面上点了合并也行，之后说同一句话，脚本只做同步和清理。小改动不开 PR，在本地合并，再把 `main` 推上去。
- **`main` 一动就推。** 有远端的项目，合并、立项验收、批准文件的提交、待办行的增删之后，脚本都把 `main` 推到 origin（plan 的批准标记在工作分支上，不动 `main`）。推送不等于发布：`deploys` 只决定「Merging publishes to production」那一行。由推送触发流水线的项目要知道，批准文件和待办行的提交也会触发一次；嫌多就在流水线里按路径忽略 `specs/**`。

### 只写不启用

- **每个 PR 自动评审**（`claude-code-action` 或托管的 Code Review 服务）。
- **CI 里的模型判断步骤**（用 `claude -p` 分析失败的构建、起草变更说明）。先只读；agent 要写任何东西都以 PR 的形式出现。
- **通过 MCP 部署**：agent 在 session 里自己发布、查状态、回滚；按环境分级的自主权。四条原则留着：不同环境用不同的工具或 server（放行规则按工具名写，不按参数）；无人值守运行用 `dontAsk`；生产环境默认关闭，只有钩子明确放行才发布；回滚事先批准、一条命令、定期演练。
- **单独的发布批准**：合并和发布分开，发布由有权的人单独批准，钩子检查针对那个确切版本的已记录批准。
- **代价不可接受的项目的三项要求**：发布前的验收环境、一条演练过的回滚命令、发布后的确定性检查。我们今天没有这一类项目。
- 什么时候拿出来：客户的 CI、有 API 预算的公司环境、有真实流量的已部署项目。

## Maintain

### v3 试行的做法

**Closing the loop on metrics**

试行的形式就是「一个入口加分流」。

- **一个入口：roadmap.md 的「To do」段。** 一条发现一行：日期、谁提的、一句话。只放**还没决定**的条目：验收时发现但不在那次改动范围内的、评审留下的、owner 提到的。
- **加一行**由脚本直接提交（只能往那一段追加），所以发现当场就记下了。
- **处置之后这一行就离开**，删除或移动由 owner 点一次确认：
  - 现在修：写 intent（带「来源」一行），删掉这一行；
  - 排期：移到 roadmap 的计划阶段里；
  - 不做：删掉。Git 历史里有。同一类要求反复出现又反复被驳回，就该写进 mission 的「不做什么」；
  - 已经直接改掉：对象不是产品文件（CLAUDE.md 的更正、一份笔记）、已经在工作分支上提交改掉的，带着那个提交的哈希删掉这一行。
- **待办行只在 `main` 上、只经脚本进出**：进来走 `todo_add.py`，离开走 `roadmap_edit.py`。在分支上直接改「To do」段——删、改写、新增——写入钩子拒绝，用 shell 改的由收尾检查查到（和分支点上的 `main` 比）。原因：飞猫 `2026-11-20-blog` 的 session 在分支上顺手删了三行，owner 的那次确认没有发生，`main` 上的行数到合并才对，把 `main` 合回分支时还冲突了。正在解合并冲突的那次编辑钩子不拦。
- **「Known limits」段单独留着**：明知如此、决定不修的缺陷。没有它，下一次评审或验收会把同一个缺陷再报一遍。缺陷修掉时那一行离开；只有在明确接受一个缺陷时这一段才变长。
- 没有「待接受的 intent」专门的存放处：决定「现在修」之前，一条发现只是它那一行；之后，草稿在自己的工作分支上。
- **不靠定期清理也不会膨胀**：每行带日期；状态脚本在会话开始时报有几行未决、最早的是哪天；每次收尾更新状态行时，能处置的顺手处置。不设过期期限。
- **收尾检查**：一个改动的每条遗留项必须指向一份新 intent、「To do」的一行、或「Known limits」的一行。
- 事故之后：代码补回归测试，配置补一个项目配置 eval 的用例（见 Test）。

### 只写不启用

- **触发循环。** 触发来源：消息和工单、定时、指标越界（只在有稳定的高频指标时）。检测是确定性的，在模型之外。
- **指标带。** 滚动窗口上的均值加标准差、漂移规则；分级写在有版本的配置里：只记录、只读诊断、提 PR 或执行事先批准的 runbook。
- **agent 自己写 intent 进分流队列。** 每条发现是一份完整的 intent.md，由 owner 分流；被驳回的发现用来调整触发条件。
- **每个由事故引出的修复自动留下一个 eval。**
- 什么时候拿出来：项目有真实流量和事故。

## 公司环境

整节只写不启用，留给以后在公司里用这套流程时参考。

- playbook 的五个角色（product owner、policy owner、tech lead、engineer、release manager）要对应到真实的人或组。
- 批准是有权的人合并 PR；存在检查读受保护的 `origin/main`。
- 托管设置里开了 `allowManagedHooksOnly` 或 `allowManagedMcpServersOnly` 时，项目自己的钩子和 MCP server 不会运行。流程的强制钩子必须通过公司批准的插件市场或托管文件下发，否则强制就退化成文字约定。
- 接外部项目：用客户的基础设施和凭据；交付物只以 PR 形式给；先问清代码能不能交给 Anthropic 的模型处理、费用谁出。
- 流程有别人用的时候，skill 的触发说法要放宽，不再是每个 skill 只测一种说法。
