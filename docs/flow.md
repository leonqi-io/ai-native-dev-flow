# 开发流程 v3 规则

这份文档是我们以后所有项目的开发流程规则。来源有三处：DEV_FLOW v2 的实践、LoomCV 上的 SDD 试行、AI-native SDLC playbook 课程。裁定的原文在 `docs/decisions.md` 指向的笔记里，这里只写结论。

**读法。** 每章分两部分：

- **v3 试行的做法**：从试点项目开始真正执行的做法。
- **只写不启用**：设计写在这里，现在不执行。每条都写了什么情况下再拿出来。

阶段用 playbook 的名字（Plan、Design、Build、Test、Deploy、Maintain），12 个 play 用课程原标题，文件用 SDD 的名字。没有内部的关卡编号。

---

## 总则

### 流程管什么

开发流程只管仓库里产品的改动：代码、站点内容、配置。用这些产品干业务的工作流程（比如用 skill 写公众号文章）不归它管。两边唯一的交接点是：有人在干业务时发现产品需要改，说出来，记成一条待办。

### 三个档位

| 档位 | 什么算这一档 | 走什么 |
|---|---|---|
| 小改动 | 用户察觉不到行为变化，或者只动一处：错字、文案、一个配置值、依赖升级、评审里发现的单处修复 | 一个文件夹，两份短文件（intent.md、validation.md），没有 spec、plan 和问答 |
| 正常档 | 其余全部 | 完整的链：intent → spec 加 validation → plan → 红测试 → 实现 → 评审 → 验收 → 合并 |
| 高风险档 | 碰到以下任何一项：不可逆的数据改动、凭据或个人数据、公开发布或部署配置、存储或输出的数据形状 | 正常档，再加：plan 在写代码前由新 session 二读；plan 写明回退路径；validation 的 §3 必填，并且在真实数据上走一遍 |

- 档位的界线是定性的，不设文件数阈值。事后核对靠评审里的固定检查「这次小改动是否改了行为」。
- 档位写在 intent.md 的 `Tier` 一行，接受后不再改。
- 小改动也有自己的文件夹，这样「为什么改、怎么改、怎么测的、留下什么没做」都查得到，不靠 Git 历史去猜。
- 不是产品的文件（笔记、roadmap 的状态行、CLAUDE.md 里两次即记的更正）直接在工作分支上提交，提交说明里写原因。凡是碰产品代码、内容、配置的，哪怕一个字，都走小改动。

### 批准记录是 `main` 上的文件

- 一份文件被批准，记录就是它在 `main` 上的已提交版本。在分支上是草稿，在 `main` 上是已接受。intent 和 spec 都没有 `Status` 字段。
- agent 只在工作分支上工作和提交。钩子拦掉一切会移动 `main` 的 git 命令，并说明该走哪条路。
- 四个批准点按批准的对象命名：

| 批准点 | 阶段 | owner 做什么 |
|---|---|---|
| intent 接受 | Plan | 读 intent.md，提交进 `main` |
| spec 接受 | Design | 在问答里裁定；读 validation.md 的 §0（有 §3 就一起读）；把 spec.md 和 validation.md 提交进 `main` |
| plan 批准 | Build | 读 plan.md 里「For the owner」一节，裁定其中的点，提交进 `main` |
| 验收和合并 | Deploy | 执行 validation.md 的 §0，读评审报告里的 Important，合并 |

- Test 阶段没有人工批准，靠钩子和 verify 命令。
- 正常档和高风险档的提交由 owner 在自己的终端里粘贴一行命令完成（`accept.py`）。小改动的两次确认各是一次点击。
- 钩子只查「在不在 `main` 上」，不锁内容。批准之后再改，会在最后的 diff 里看到，并计入度量。
- 只有合并之后才有意义的验收，在集成分支上跑；把集成分支合进 `main` 就是批准。

### owner，没有角色表

规则和模板里只用一个词：owner。个人项目上五个角色都是同一个人，角色表在实际操作里不起作用。真正起作用的只有两处：spec 里每条 concern 的 owner（比如飞猫的品牌和内容归 Kitty），以及 intent 用谁的话写、由谁确认。

owner 需要到场的时刻：上表四个固定点。中途只在三种情况下被叫到：测试文件的改动需要放行；一条 Important 要求改 spec.md 或 plan.md；validation §2 的某项检查怎么也过不了。owner 不写测试，不读代码，不读 §1 和 §2。UI 改动的验收需要他坐在屏幕前。

### 评审的 session 不是实现的 session

正常档和高风险档必须遵守。小改动例外：不另开 session，由 verifier 带着 REVIEW.md 的固定检查在实现的 session 里给出评审结论。这个例外带四条兜底：

1. verifier 不靠任务说明干活：它自己读 `main` 上的 intent 和分支对 `main` 的 diff，任务说明只有文件夹名。
2. 合并提示里列出改动的文件和行数，由 owner 自己看，不设行数阈值。
3. 独立评审推后而不取消：下一次新 session 的评审把此前合并的小改动逐个读一遍，判断行为变了没有，记进各自的 Approval log。状态脚本报告还有几个小改动没被读过。被判为「本该走正常档」的个数是试点后决定要不要收紧的依据。
4. 小改动碰到项目声明的高风险路径，合并脚本直接拒绝。

兜不住的部分：合并之后、下一次新 session 评审之前，改了行为的小改动已经在线上。坏发布代价可接受的项目接受这一点（回退那次合并）。

### 每个改动一个文件夹，状态从 Git 读

- 文件夹是 `specs/<日期>-<slug>/`，工作分支和文件夹同名。`specs/` 顶层放 mission.md、tech-stack.md、roadmap.md。按日期排列的文件夹就是全部改动的索引，大小改动都在。
- 现在在哪个阶段，由状态脚本从仓库推出来：当前分支对应哪个文件夹，intent、spec、validation、plan 哪些在 `main` 上，红测试提交了没有。钩子查的是同一批事实。会话开始时钩子自动跑一次状态脚本。

### skill 和启动方式

- 每个步骤是一个 skill，用平常话触发，没有带参数格式的命令。保底的启动方式是 `/flow:<名字>`；名字后面跟的内容当作普通指令读。
- 每个 skill 结束时用一句话说下一步是什么。
- 清单、每个 skill 测试通过的说法：见 `docs/skills.md`。

### 钩子分三类

- **直接放行或拒绝，不需要人**：移动 `main` 的 git 命令、存在检查。
- **问操作者（`ask`）**：只用在操作者有权批准的地方。个人项目上 owner 就是操作者：小改动的两次点击、测试文件的放行、roadmap 待办行的删除和移动。
- **检查一份已记录的批准**：批准人是别人时用。个人项目上就是「文件在不在 `main` 上」。agent 没有办法自己写出它要被检查的那份记录。

拒绝时总是说明该走哪条路。界限：按模式匹配的拦截挡得住 agent 越过批准，挡不住人绕过去。

### 模型

哪一步用哪个模型，是用户级的设定，不在流程核心里：见 `plugin/templates/user/model-table.md`。要点：日常用 Opus，实现和小改动用 Sonnet，结果不够好先加 effort 再换模型，Fable 只在三种情况下一开始就用。

## 立项

在六个阶段之前，每个项目做一次。

### v3 试行的做法

- 写三份项目级文件，放在 `specs/` 顶层：
  - **mission.md**：用户是谁、带着什么来、带着什么走、中间做什么、这个产品不做什么。只有这五个标题，一屏左右。用处有三个：问答时先查它，查得到的范围问题不再问；每份 intent 的「Out of scope」对着它写；Maintain 阶段据此驳回一条待办。
  - **tech-stack.md**：CLAUDE.md 没有锁定的技术决定，包括部署形式；用一句话回答「生产环境宕机或出错几天，代价是什么」；要部署的项目写明凭据放在哪。写 spec 时它是约束的来源。
  - **roadmap.md**：顶部的状态行（下次从哪里接着做）、按顺序的计划阶段、「To do」段、「Known limits」段。
- 同一步里写好项目的 CLAUDE.md、REVIEW.md、`.claude/flow.json`。仓库里有 `.claude/flow.json`，钩子才动作。
- **立项也跑问答**，规则是 Plan 一章「问答是有界的多轮」那一条：先把三份文件和 `.claude/flow.json` 的五项都起草出来，一轮的问题一起给，每裁定一条把剩下的连同默认答案再列一遍。和单个改动有三处不同：mission 和 tech-stack 正是要写的东西，「先查」查的是仓库里已有的文档；完整性清单是给单个改动写的，这里不用，只在「这一轮没让草稿发生任何变化」时停；停下时还没定的，记成 roadmap「To do」段的一行，不再问。
- 批准方式和其他文件一样：owner 提交进 `main`。以后改这三份文件，同样是 owner 提交，提交说明里写原因。
- 一份 intent 和 mission 冲突时，先改 mission，再接受 intent。没有哪份 intent 可以悄悄越出范围。
- 三份文件不全在 `main` 上时，状态脚本报「项目未立项」。
- `.claude/flow.json` 只存脚本和钩子要读的五项：`test_scope`、`deploys`、`pull_request`、`high_risk_paths`、`non_product_paths`。verify 命令在 CLAUDE.md，坏发布的代价和凭据位置在 tech-stack.md，权限清单在 `.claude/settings.json`。任何 policy 都不进这个文件。

### 只写不启用

没有。

## Plan

### v3 试行的做法

**Capture as intent.md**

- 一份 intent 只讲一个改动：问题（带一个数）、想要的结果、受影响的人和系统、约束、未决问题、不做什么、来源。写「要什么、为什么、为谁」，不写「怎么做」。
- 「来源」一行写谁提的、什么时候，或者是哪个改动的遗留项，这样能倒着查回去。
- intent 和 spec、validation、plan 放在同一个文件夹里。
- **问答是有界的多轮。** 每一轮都挂在一份草稿上：先按已知的写草稿，问题从草稿的缺口来，答案更新草稿。一个问题要同时满足三条才问：仓库、mission 和 policy 里查不到答案；带默认答案；说明答错了要返工多少。一轮的问题一起给；每裁定一条，把剩下的连同默认答案再列一遍。
- **什么时候停。** 完整性清单满足了，或者这一轮没让草稿发生任何变化。清单是：问题带一个数；每条约束在 spec 里有位置；空、错误、首次使用、再次使用四种状态写了；不做什么写明了；没有无主的 concern。停下时还没解决的，记成 concern，不再问。
- **问答用在哪。** 立项、intent、spec 三处。plan.md 和评审不跑问答。plan：需求在 spec 里已经问完，剩下的是实现上的选择，列在「给 owner 的一节」里各带默认、一次裁完；这里还要多轮问，说明 spec 那轮问粗了，由「问得太粗」那项度量去抓。评审：价值在新 session 独立读、独立下结论，边评边问 owner 就又依赖实现时的语境；讨论放在 owner 读完报告、裁 Important 的时候。
- owner 不是开发者时（飞猫），给她的问题少、用她的话、一批问完，由开发者转达。
- 问答抓不到两类东西：只有在屏幕上才看得出的（靠 mock），只有读代码才发现的（靠在某个 HEAD 上核过的事实和 plan 批准）。
- **小改动**：owner 或者发现问题的 session 说「按小改动处理」，agent 起草四五行的 intent，弹出确认，owner 点一次；之后自动往下做，停在合并前。

### 只写不启用

- **正常档和高风险档也用一次点击确认。** 试点之后再决定。
- **agent 自己写完整的 intent 放进队列。** 这是给无人值守的维护循环用的形式，见 Maintain。

## Design

### v3 试行的做法

**Requirements and design**

- **spec.md**：需求是原子的、可测的，一条一个 R-ID，包括空、错误、首次使用、再次使用四种状态；设计；intent 里每条约束和每个未决问题的去向；researcher 在某个 HEAD 上核过的代码事实；对以前决定的修改；带编号的 concern（类别、提议、owner、裁定），裁定直接写进那一行。
- **validation.md** 是独立的文件，在 plan 之前写。正常档六段，按「谁来执行」分：

| 段 | 谁执行 | 内容 |
|---|---|---|
| §0 owner 的部分 | owner | 他唯一要读的一段：一次性的准备；每一步是能直接粘贴的命令块，加一句预期结果；真实数据那边不能碰什么；要他给出的判断 |
| §1 测试要求 | 实现的 session | 每个要断言的行为一行，引用 R-ID。plan 据此给测试命名和计数；判断「红测试事后有没有被削弱」也看这张表 |
| §2 机器检查 | verifier、评审的 session | 这个改动特有的检查：一条命令加预期输出。没有就省略 |
| §3 预期变化 | owner | 只在验收会碰真实数据或真实环境时写：什么会变、什么必须逐字节不变、比较用的命令。高风险档必填 |
| Leftovers | 收尾检查 | 每条指向一份新 intent 或 roadmap 的一行 |
| Approval log | 脚本和人 | 放在最后，只追加 |

- 没有单独的「失败」清单：§0 或 §2 的任何一步和预期结果不符，就是失败。
- 小改动的 validation.md 是五项：改了什么（一行）、verify 命令和粘贴的输出、评审结论、遗留项、Approval log。
- **R-ID 覆盖检查。** 把 validation.md 提交进 `main` 等于批准整份文件，而 owner 只读 §0 和 §3。所以有一个脚本把关：spec.md 的每个 R-ID 至少要出现在 §0、§1、§2 之一，否则拒绝提交。「有没有哪条需求没人检查」由脚本回答。
- 每条命令在写的时候由 researcher 对着「执行那一步时仓库的状态」试跑一遍。
- UI 改动先出 mock，问版面和措辞的问题对着 mock 问。
- 改动碰到产品调用的模型的行为（提示词、模型、检索参数、阈值）时，§2 写上项目的产品 eval 命令和预期结果。这是规则里和产品 eval 唯一的连接点。

### 只写不启用

- **一遍成稿、事后一次性提问。** playbook 的形式是 Claude 一遍写完 spec，把问题列成 concern 清单问一次。那是给无人值守运行设计的；我们用上面的多轮问答。

## Build

### v3 试行的做法

**Plan mode**

- plan.md 在 plan mode 里起草。内容：给 owner 的一节（要他裁定的点、什么可能坏、最险的一步、放弃了哪些方案）；会改的文件；工作顺序（先是 §1 的测试，按行命名和计数）；风险；证据（UI 改动包括「截图和 mock 一致」）。每一行引用 R-ID 或 concern。
- 标准：一个不了解背景的人只凭这份 plan 就能实现。
- 实现时偏离 plan，在同一次提交里更新 plan.md。脚本在收尾前比对：改了的产品文件必须在 plan 的文件清单里。
- 高风险档：plan 写明回退路径（坏发布代价可接受的项目只需写明路径，不演练）；owner 提交之前，由一个新 session 把 plan 再读一遍。

**The CLAUDE.md**

- 项目的 CLAUDE.md 控制在一页以内：命令和健康输出的样子、「Verifying your work」一段、规范、架构、Claude 在这里容易犯的错、指路。
- 两次即记：同一个错被纠正两次，就在第二次纠正的那个 session 里写进 CLAUDE.md。评审里第二次指出的错也一样。评审还要指出哪一行被这次改动弄过时了。
- 用户级的 `~/.claude/CLAUDE.md` 放我们对 agent 写的代码的规范：名字说清装的是什么（长名字可以）、难懂的地方和「为什么」要有注释、注释和代码一起改。

**Skills as institutional knowledge**

- policy 是规则，config 是项目设定，skill 是把规则包装给 Claude 用的建议性手段。三者不混：policy 不进 config。
- 一条必须成立的规则，背后要有一个脚本，skill 和钩子用同一个脚本。
- 新的 skill 和新的 subagent 都是「收割」出来的：同一件事在主 session 里手工做过两三次之后才做成 skill 或 subagent。

**Parallel sessions and subagents**

- 核心带三个 subagent，都只汇报不动手：
  - **researcher**：读代码和文档，带文件、行号和 HEAD 报事实；提问之前先查；数据形状要变时列出现有断言；试跑 validation 的命令。
  - **verifier**：在 session 说「做完了」之前跑 verify 命令，查改动的行为和最近的两条流程，逐条对 plan.md；UI 改动对 mock 截图，观察一次调用的全程。
  - **code-reviewer**：按我们的规范查 diff：命名、注释、长函数、深嵌套、重复逻辑。
- 项目可以在自己的 `.claude/agents/` 下加 subagent（飞猫大概会有一个对照内容规则的检查，能用脚本做的用脚本）。
- 并行：一条流一个 worktree，从两条开始，上限由评审跟不跟得上决定。plan 里写「Parallel split」：共用的一步先做完并冻结，各条流的文件互不重叠，合并顺序和合并后的检查。
- 浏览器在测出结果之前按最保守的读法：一次只给一个 session 用。

### 只写不启用

- **同一个规则脚本在 CI 里再跑一遍。** 等项目有了 CI 再加。
- **auto mode。** `ask` 在自动批准模式下还弹不弹，试点第一天才测；测完之前不靠它。
- **第四个 subagent。** 最可能的是高风险档 plan 的二读；现在由新 session 手工做，做够两三次再说。
- **两条以上的并行流。**

## Test

### v3 试行的做法

**Give Claude a feedback loop**

- 一条 verify 命令，写在 CLAUDE.md 里，实现时反复跑到绿。「做完了」的证据是粘贴出来的原样输出，不是对输出的描述。
- 每个正常档和高风险档的改动都先写红测试：按 §1 写测试，先对测试文件跑格式化，跑 verify 确认它们因为需求还没实现而失败，把原样输出存成 `red-run.txt`，和测试一起提交在工作分支上。
- **测试锁。** 从红提交起到合并为止（小改动是整条分支），对测试范围内文件的每次 Edit 和 Write 都会弹 `ask`，显示是哪个文件。测试范围在 `.claude/flow.json` 里声明；新增测试文件也算。
  - 正当的测试修复：owner 批准提示，改动发生，agent 在 Approval log 里记一行：哪个文件、为什么、属于 §1 的哪一行。
  - 收尾前的检查：脚本比对红提交和当前状态之间测试范围的差异，每个有变动的文件必须有放行记录，否则拒绝。这样不管是谁改的（格式化工具、shell 命令）都查得到。
  - 「红测试是否已提交」由状态脚本从 Git 读 `red-run.txt`，没有标志文件，也不存哈希。
- UI 改动由实现的 session 在浏览器里自查：实现、截图、和 mock 比，两三轮，然后才给人看。

**Continuous evals in CI**

「eval」这个词不单独用，因为它指三样不同的东西：

| 名字 | 测什么 | 放在哪 | v3 怎么跑 |
|---|---|---|---|
| 插件 eval | `flow` 插件的 skill 在平常话下会不会被选中 | 本仓 `plugin/evals/`，官方 `claude plugin eval` 的格式 | 启用。手动，在 owner 的终端里，用订阅登录、不配 API key；`--ablation none`，每个用例跑三次，只用确定性检查。改了某个 skill 的 description 之后跑它的用例；试点开始前整套跑一次。不定期跑 |
| 项目配置 eval | 一个项目的 CLAUDE.md 和项目钩子能不能让 Claude 把活干到标准 | 那个项目的 `evals/`，课程第 9 节的格式 | 只有两种由事件触发的手动用法，见下 |
| 产品 eval | 产品调用的模型表现如何 | 项目自己定 | 项目自己的事。规则只管一个连接点：validation §2 |

- 项目配置 eval 的两种用法：**删除或重写配置之前**（精简 CLAUDE.md、重写一个 skill），给每条要删的内容写一个用例，在交互 session 里手动跑，确认行为没变；**agent 写的代码引发事故之后**，代码补回归测试，配置补一个用例。每个用例跑三次才算数。
- 不定期跑的理由：我们的配置只有 owner 和我们的 session 在改，几乎都是加一行；配置变差会在真实工作里表现为一次通过率下降、修复轮数变多、同样的错重复出现，这些从 Git 和 Approval log 读得到。
- LoomCV 的 `dev_flow/eval/t1/` 全部是产品 eval，原地不动。

### 只写不启用

- **项目配置 eval 的 CI 形式**（每次改 CLAUDE.md、`.claude/`、`evals/` 就跑核心子集）和**定期形式**（整套按周期跑）。
- **多少次运行才可信。** 单次运行不算数。一个用例在某份配置下过不过，按每个用例三次运行判断，和官方插件 eval 的默认值一致；三次结果不一致时，先把用例的检查改得更确定，再重跑。
- **用例从哪来。** 近期真实任务加上每次由 agent 代码引发的事故；一个用例要先在旧配置下失败才算数；素材就是 `specs/` 下的历史（之前的提交、当时的 intent、plan 的文件清单、validation §2）。
- 什么时候拿出来：项目有了真实流量和事故；公司环境里有 API 预算；或者上面那几个度量无缘无故变差。
- 关于费用：用订阅登录时，`claude -p` 用的是订阅自己的额度，不另外花钱。不启用的原因是我们的项目多数是小的个人项目，没有上 CI 和遥测循环的理由，而且每周额度也是实在的成本。

## Deploy

### v3 试行的做法

**AI in the PR review loop**

评审分三层，各管各的：

1. **code-reviewer**：实现 session 里的 subagent，只看规范和可读性，在那个 session 说「做完了」之前。
2. **读 REVIEW.md 的评审**：新开的 session，固定的三遍（bug 和逻辑、安全、对 spec.md 和 plan.md 的符合度），每条发现标 Important 或 Nit。它不是 subagent，因为 subagent 是由它要评判的那个 session 交代任务的。
3. **验收和批准**：owner 执行 validation.md 的 §0，然后合并。

- 第一层和第二层的分工写在 REVIEW.md 的「Do not report」里：风格和可读性归 lint 和 code-reviewer。
- 每条 Important 都要写怎么确认（一条命令，或 validation 的某一步）。
- 评审的 session 不改代码。例外：单处修复可以当场按小改动做掉并记录。
- 修复轮：实现的 session 处理评审意见；修完后回到评审的 session 复核，由它在 Approval log 里追加新的一行。实现的 session 不自己写评审结论。
- 评审结论在两类项目里都记进 validation.md 的 Approval log，合并前的检查只读这一处。有 PR 的项目另外把报告贴成 PR 评论。
- code-reviewer 留不留，试点之后判断，事先不设阈值：数它的发现里有多少导致了代码改动。

**Hooks as approval gates**

钩子和脚本的完整清单见 `docs/hooks-and-scripts.md`。合并之前，脚本确定性地检查：每份文件的形状、R-ID 覆盖、测试范围的差异、plan 对照、遗留项的指向、评审结论里没有未处理的 Important。任何一项不过就拒绝，并说明缺什么。

**CI/CD integration and deployment**

- **对每个要部署的项目只有一条硬要求**：部署凭据放在 agent 够不到的地方（CI 的 secret 存储），由合并触发部署。它不增加工作量，并且保证「不合并就不会上线」。
- 其余要求按坏发布的代价分级，依据是 tech-stack.md 里那一句话：
  - **代价可接受**（飞猫）：不设 staging，发布前在本地预览里验收；回退就是一行字「回退那次合并」，不演练；不要求发布后的自动检查。
  - **代价不可接受**：见「只写不启用」。
- **合并就是发布批准**（代价可接受的项目）。合并触发部署，所以 owner 的合并同时批准了代码和发布，没有单独的发布步骤。合并前的确认要写明后果：小改动的合并提示里带一行「Merging publishes to production」；走 PR 的改动，这一行放在 PR 描述的固定位置。
- **个人项目上的批准就是 owner 自己的合并。** GitHub 不允许作者批准自己的 PR；缺少的第二个人的检查，由独立的评审 session 和 owner 自己的验收补上。
- **开不开 PR 按项目定**，写在项目的 CLAUDE.md 和 `.claude/flow.json` 里：有远端和部署流程的项目开 PR；只在本地的项目不开，评审在分支对 `main` 的 diff 上做。

### 只写不启用

- **每个 PR 自动评审**（`claude-code-action` 或托管的 Code Review 服务）。
- **CI 里的模型判断步骤**（用 `claude -p` 分析失败的构建、起草变更说明）。先只读；agent 要写任何东西都以 PR 的形式出现。
- **通过 MCP 部署**：agent 在 session 里自己发布、查状态、回滚；按环境分级的自主权。四条原则留着：不同环境用不同的工具或 server（放行规则按工具名写，不按参数）；无人值守运行用 `dontAsk`；生产环境默认关闭，只有钩子明确放行才发布；回滚事先批准、一条命令、定期演练。
- **单独的发布批准**：合并和发布分开，发布由有权的人单独批准，钩子检查针对那个确切版本的已记录批准。
- **代价不可接受的项目的三项要求**：发布前的验收环境、一条演练过的回滚命令、发布后的确定性检查。我们今天没有这一类项目。
- 什么时候拿出来：客户的 CI、有 API 预算的公司环境、有真实流量的已部署项目。

## Maintain

### v3 试行的做法

**Closing the loop on metrics**

试行的形式就是「一个入口加分流」。

- **一个入口：roadmap.md 的「To do」段。** 一条发现一行：日期、谁提的、一句话。只放**还没决定**的条目：验收时发现但不在那次改动范围内的、评审留下的、owner 提到的。
- **加一行**由脚本直接提交（只能往那一段追加），所以发现当场就记下了。
- **处置之后这一行就离开**，删除或移动由 owner 点一次确认：
  - 现在修：写 intent（带「来源」一行），删掉这一行；
  - 排期：移到 roadmap 的计划阶段里；
  - 不做：删掉。Git 历史里有。同一类要求反复出现又反复被驳回，就该写进 mission 的「不做什么」。
- **「Known limits」段单独留着**：明知如此、决定不修的缺陷。没有它，下一次评审或验收会把同一个缺陷再报一遍。缺陷修掉时那一行离开；只有在明确接受一个缺陷时这一段才变长。
- 没有「待接受的 intent」专门的存放处：决定「现在修」之前，一条发现只是它那一行；之后，草稿在自己的工作分支上。
- **不靠定期清理也不会膨胀**：每行带日期；状态脚本在会话开始时报有几行未决、最早的是哪天；每次收尾更新状态行时，能处置的顺手处置。不设过期期限。
- **收尾检查**：一个改动的每条遗留项必须指向一份新 intent、「To do」的一行、或「Known limits」的一行。
- 事故之后：代码补回归测试，配置补一个项目配置 eval 的用例（见 Test）。

### 只写不启用

- **触发循环。** 触发来源：消息和工单、定时、指标越界（只在有稳定的高频指标时）。检测是确定性的，在模型之外。
- **指标带。** 滚动窗口上的均值加标准差、漂移规则；分级写在有版本的配置里：只记录、只读诊断、提 PR 或执行事先批准的 runbook。
- **agent 自己写 intent 进分流队列。** 每条发现是一份完整的 intent.md，由 owner 分流；被驳回的发现用来调整触发条件。
- **每个由事故引出的修复自动留下一个 eval。**
- 什么时候拿出来：项目有真实流量和事故。

## 公司环境

整节只写不启用，留给以后在公司里用这套流程时参考。

- playbook 的五个角色（product owner、policy owner、tech lead、engineer、release manager）要对应到真实的人或组。
- 批准是有权的人合并 PR；存在检查读受保护的 `origin/main`。
- 托管设置里开了 `allowManagedHooksOnly` 或 `allowManagedMcpServersOnly` 时，项目自己的钩子和 MCP server 不会运行。流程的强制钩子必须通过公司批准的插件市场或托管文件下发，否则强制就退化成文字约定。
- 接外部项目：用客户的基础设施和凭据；交付物只以 PR 形式给；先问清代码能不能交给 Anthropic 的模型处理、费用谁出。
- 流程有别人用的时候，skill 的触发说法要放宽，不再是每个 skill 只测一种说法。
